# 图库排序响应、扫描恢复与版本展示设计

日期：2026-08-10  
目标版本：1.0.2

## 背景与已确认问题

首次打开图库且增量扫描仍在运行时，切换“最早优先”可能让 Windows 将窗口标记为“未响应”。当前排序动作会同步读取完整图库快照，照片详情和多张可见预览也通过同步 Tauri 命令读取机械盘；这些工作共享窗口事件线程。切换排序后还会保留原照片，因此从“最新优先”切到“最早优先”时会跳到列表末尾，并立即读取一组未缓存照片。

当前运行的旧安装版与新测试版都标记为 1.0.1。新测试版已把数据库迁移到 schema 9，而旧安装版只支持 schema 8，所以旧版安全地进入只读模式。扫描虽不修改照片文件，却必须写入索引数据库；因此“继续扫描”无法成功。界面目前丢失了数据库进入只读模式的具体原因，并仍展示可点击的“继续扫描”。

## 目标

- 图库快照、照片详情和预览的 SQLite/磁盘读取不得阻塞 Tauri 窗口事件线程。
- 切换“最早优先”后选中排序结果中的第一张最早照片；切换“最新优先”后选中第一张最新照片，不保留原选择。
- 图库页面切换排序时只请求当前页面需要的数据，避免无用的待删除完整快照。
- 数据库只读或写入器不可用时，扫描重试必须立即返回可解释错误，不能先显示启动成功再后台失败。
- 数据库来自更新版本时，界面明确提示安装新版并禁用“继续扫描”。
- 应用版本升级为 1.0.2，并在所有界面右下角统一显示构建包的真实版本。
- 不改变照片文件的只读扫描边界，不放宽 Import、Recycle 或数据库安全门。

## 非目标

- 本次不引入分页图库协议，不重做时间线数据模型。
- 本次不新增图像解码依赖或重做独立缩略图渲染管线。
- 本次不自动覆盖安装旧程序，也不自动恢复或替换数据库。
- 本次不改变扫描、导入、回收站对真实照片文件的安全约束。

## 设计

### 1. 后台化只读图库命令

将可能执行 SQLite 查询、文件身份复核、机械盘读取或 Base64 编码的图库命令改为异步 Tauri 命令。命令进入后只克隆受管理的 `Arc` 服务，并通过 `tauri::async_runtime::spawn_blocking` 执行现有同步领域逻辑：

- `get_library_snapshot`
- `get_photo_detail`
- `get_photo_preview`
- `get_pending_delete_snapshot`

同步领域函数仍保留明确的 `Result<_, DomainError>` 边界。后台任务 join 失败统一转换成内部错误，不暴露线程实现细节。轻量的纯内存状态查询不做无意义后台化。

预览仍复用现有 `IoScheduler`：当前照片和可见胶片缩略图最多按机械盘并发上限读取，浏览活动继续压低扫描和后台缓存任务优先级。此改动解决窗口事件线程被阻塞的问题；独立缩略图编码留给后续分页/缓存优化，不纳入本次修复。

### 2. 排序数据流与选择语义

图库路由切换排序时：

1. 保留当前画面作为加载占位，禁用重复排序请求。
2. 仅请求目标排序的图库快照。
3. 请求成功后原子更新 `sortMode`、图库快照和 `selectedPhotoId`。
4. `selectedPhotoId` 固定设为新快照 `photos[0]`；空图库则设为 `null`。

待删除路由切换排序时仍同时刷新图库摘要与待删除快照，因为该页面需要两者的一致状态；选中项固定为新待删除列表的第一项。

若请求失败，保留原排序、原快照和原选择，并显示错误。排序请求完成前不得保存错误排序模式下的浏览游标。

### 3. 扫描重试与只读数据库诊断

`retry_library_scan` 在创建后台扫描前检查数据库模式和写入器健康状态：

- 数据库为 `ReadOnlySafe` 或 `Unavailable` 时，直接返回数据库保存的安全模式原因。
- 数据库标记为 `ReadWrite` 但写入器不健康时，直接提示安全退出并重新启动。
- 只有数据库可写且写入器健康时才启动扫描线程。

运行时安全状态在数据库只读时优先展示 `Database::safe_mode_reason().user_message`，使“数据库来自更新版本”等原因能够到达界面；内部 diagnostic 不发送到前端。

扫描页接收安全状态。当数据库不可写或写入器不健康时：

- “继续扫描”保持可见但禁用，避免用户误以为功能消失。
- 按钮附近展示明确原因；数据库版本过新的文案要求安装最新版。
- “重新选择照片文件夹”不能伪装成数据库修复手段，仍只负责 Root 重连。

正常数据库不受 Import/Recycle 独立门关闭的影响，仍允许只读文件扫描写入索引。

### 4. 版本号来源与布局

同步更新以下版本来源为 1.0.2：

- `package.json` 及锁文件
- `src-tauri/Cargo.toml` 及锁文件中的本包版本
- `src-tauri/tauri.conf.json`

Vite 构建从根 `package.json` 注入只读编译常量，React 不维护第二份硬编码版本。应用根节点渲染一个全局版本标签 `v1.0.2`：

- 固定在窗口右下角，在图库、待删除、扫描、导入、设置和启动状态中一致可见。
- 状态栏为标签预留右侧空间，避免覆盖待删除入口或安全状态。
- 标签不接受点击或键盘焦点，不改变现有操作顺序。

构建检查必须验证前端、Cargo 与 Tauri 配置版本一致，防止再次出现“同一版本号、不同数据库能力”的安装包。

## 错误处理

- `spawn_blocking` join 失败映射为稳定的中文内部错误；原有领域错误原样返回。
- 排序失败不提交部分前端状态。
- 扫描不可重试的原因同时出现在扫描页正文和操作错误区域，但不展示路径之外的内部诊断。
- 数据库版本较新属于兼容性保护，不归类为数据库损坏，不建议重建或删除数据库。

## 测试与验收

### Rust

- 异步命令包装保持领域错误传播，并覆盖后台任务错误映射辅助函数。
- 扫描重试在只读数据库下同步拒绝，不创建新的 `scan_run`。
- 数据库安全状态返回版本过新/只读的用户可见原因。
- 正常可写数据库仍可启动重试扫描。

### React

- `captureAsc` 成功后选中目标快照第一项；`captureDesc` 同理。
- 图库路由排序不请求待删除完整快照；待删除路由仍保持双快照一致刷新。
- 排序失败保留原排序和选择。
- 数据库只读时“继续扫描”禁用并显示原因；正常数据库时可点击。
- 所有主要路由均显示 `v1.0.2`，且版本标签不覆盖状态栏交互。

### 回归与构建

- 前端单元测试、端到端测试、Rust 全目标测试、Clippy、安全审计和生产构建通过。
- 生成 1.0.2 Windows 安装包，确认文件版本、产品版本和界面版本一致。
- 使用可丢弃测试图库验证：首次启动扫描期间反复切换排序，窗口保持响应；两种排序均定位第 1 张。
- 使用 schema 高于测试程序支持范围的数据库副本验证：程序只读打开、提示升级、续扫禁用，数据库文件不被修改。

## 发布与现有数据

1.0.2 支持当前 schema 9，不新增数据库迁移。用户安装 1.0.2 后可直接打开已被新测试版升级的数据库并恢复正常扫描。旧 1.0.1 仍会安全只读；界面修复只存在于 1.0.2，因此交付时必须明确要求退出旧程序并安装新包。

# 本地 Fuji 照片管理器 v1：阶段 8 规模硬化与发布设计

日期：2026-08-08

## 1. 范围与依据

本设计只实施既有分阶段计划中的“阶段 8：规模硬化与 v1 发布”。它服从并且不修改以下已确认文档：

- `2026-07-28-local-photo-manager-design.md`
- `2026-07-28-local-photo-manager-ui-design.md`
- `2026-07-29-local-photo-manager-import-location-ui-design.md`

- `2026-07-28-local-photo-manager-implementation-plan.md`

阶段 8 不增加产品功能。搜索、历史重复扫描、相似照片、完整 RAW、专业选片、多图库 UI、手动清理缓存和永久删除均不在范围内。

## 2. 测试数据与磁盘边界

所有生成图库、ImportSource、FujiLibrary、CacheRoot、数据库/AppData 沙箱、稀疏文件、回收站夹具和原始运行期报告都必须位于：

`G:\test\local-photo-manager-phase8\<run-id>`

测试结束且候选绑定复核通过后，允许把最终的小型机器可读证据和人工报告复制到 D 盘仓库的 `artifacts/` 与 `docs/`，用于本地 Git 提交。原始夹具、数据库、缓存、临时文件、截图运行目录和大体积性能数据不得复制到 D 盘。

`G:\test\Fuji-XM5` 及 `G:\test` 下其他既有对象一律视为用户数据，不用作测试输入，不修改，也不删除。D 盘只保留既有源码和构建工作区，不作为阶段 8 测试卷，也不存放测试夹具。Windows 候选安装包使用正常系统安装位置；其测试数据仍只指向 G 盘专属测试 Root。

每个 Run 在写入前必须验证：

- 目标解析后仍位于本 Run 专属目录；
- G 盘为 NTFS，专属目录及祖先不是 reparse point；
- 本 Run 拥有不可伪造的测试 Root 标记；
- 实际分配空间硬上限为 300 GB；
- 生成器和清理器只能处理具有本 Run 所有权记录的对象。

达到空间上限、无法证明目录所有权、卷或目录身份变化时立即停止。清理不得递归处理 `G:\test`，也不得接触其他 Run 或无关文件。

规模测试使用完整的 100,000 Photo、200,000 Asset 数据模型和至少 1 TB 的 Asset 逻辑总容量。文件系统通过 NTFS 稀疏生成文件表达逻辑容量；另以实际分配的可丢弃样本测量读取和 I/O。报告必须分别披露逻辑容量、实际 allocated size 和实际读取字节，不得把稀疏逻辑容量描述为实际写满或读取 1 TB。

## 3. 规模、性能与 I/O 调度

规模工具必须验证精确 Photo/Asset 行数、关系、稳定排序键、覆盖索引、分页、LRU 查询、定向重扫和恢复协调查询。它记录 wall-clock、p50/p95、进程峰值内存、I/O 字节、队列深度、并发度、吞吐、SQLite 查询计划和失败原因。

候选构建必须达到上位规格第 15.4 节的全部指标：

| 指标 | 门槛 |
|---|---:|
| 已有索引启动到可操作 | ≤ 3 秒 |
| 缓存命中切图 | p95 ≤ 150 ms |
| 未缓存照片显示反馈 | ≤ 100 ms |
| 未缓存照片出现可用预览 | p95 ≤ 2 秒 |
| `D/R` 持久化并完成切换 | p95 ≤ 250 ms |
| 10 万 Photo 常驻内存 | ≤ 1.5 GB |
| 后台任务期间缓存切图退化 | p95 不超过空闲时 2 倍 |
| 暂停或取消后台任务响应 | ≤ 2 秒 |

I/O 调度保持既有优先级：当前照片和附近预览、标记与分页元数据、导入当前文件、增量扫描与 EXIF、候选哈希和低优先级缓存。连续浏览时暂停或强力限速后台哈希，空闲后恢复。机械硬盘使用有限并发和顺序读取优先；测试必须通过 Windows 设备属性确认 G 盘介质类型。无法证明 G 盘是机械硬盘时，机械盘校准项不得通过，也不得用模拟数据冒充真实硬件测量。

## 4. 缓存硬化

缓存测试覆盖：

- 默认 32 GB 和绝对最大 64 GB；
- `max(CACHE_MIN_RESERVE_BYTES, ceil(卷容量字节数 × 10%))` 安全余量；
- 达到容量或余量门槛后的安全 LRU；
- 缩容后的后台渐进淘汰；
- 位置/容量变更必须确认，取消不改变设置；
- Active 与 Draining Root 可同时拥有同一 Asset/version/render key 的不同 incarnation；
- Evicted/Missing 后以新 Entry、ordinal、nonce 和全历史唯一路径重建；
- NeedsAttention incarnation 阻止静默再生；
- Root 离线、盘符复用、Root/文件身份变化时停止；
- 专属父目录中的无关文件始终不变。

每次淘汰先提交 `CacheEvictionIntent` 和 cache-owned `OperationReservation`，再通过同一已验证句柄处理精确对象。测试覆盖 Intent、句柄打开、身份校验、删除、关闭、路径缺失复核和结果提交的全部故障边界，以及校验后同路径出现替代对象的竞态。生产路径不得出现按路径 `remove_file` 或递归清理父目录。

## 5. SQLite、备份、迁移和安全模式

所有连接必须验证 `foreign_keys=ON`、`journal_mode=WAL`、`synchronous=FULL` 和有界 `busy_timeout`。测试受控 WAL checkpoint、长读事务限制、COMMIT 失败和 `BUSY/IOERR/FULL/CORRUPT`，确保新照片文件动作立即停止、可读报告保留、Import 与 Recycle 共享写入门同时关闭。

备份必须使用 SQLite Online Backup API 或等价一致机制。验证每天首次启动快照、最近 7 个日常版本、最近 3 个升级前版本，以及 Root、VolumePolicy、ViewingCursor、标记快照、Import/Recycle Attempt、Reservation、不可变 Fact、OperationReport、OperationResolutionEvent 和缓存所有权的恢复。

迁移从每个已发布 schema 版本逐级执行：

1. 校验 schema 版本、迁移 checksum、`quick_check` 和 `foreign_key_check`；
2. 创建升级前一致快照，失败则禁止升级；
3. 在排他窗口执行前向迁移并检查最终 COMMIT；
4. 复核行数、FK、唯一约束、状态枚举和不可回退 Fact；
5. 故障时关闭新连接并恢复升级前快照，不以半迁移状态运行。

完整性、FK、VolumePolicy、唯一性或状态/报告映射矛盾时只读启动，不静默修复不可回退事实。AppData 空间不足使用 G 盘专属沙箱中的确定性配额或故障注入触发，不耗尽系统盘。旧备份恢复后先重新观察文件系统，不自动重放旧 Import/Recycle，也不覆盖、回收、采用或清理无法解释的正式文件、partial 或缓存。

## 6. DPI、键盘、对比度与窗口缩放

可访问性验收覆盖 100%、125%、150% DPI，以及 1440×900、1280×720、1100×700 窗口。候选二进制生成并人工检查图库、待删除、导入、设置、报告、长路径、错误、确认数量和问题状态截图。

自动与人工检查包括：

- 所有动作键盘可达且有清晰焦点环；
- `←/→/D/R`、auto-repeat、pending 阻止、输入框和模态框作用域；
- 模态框关闭后焦点回到发起按钮；
- 普通正文对比度至少 4.5:1，大文字和图标至少 3:1；
- 关键状态不只依赖颜色或 hover；
- 点击目标原则上不小于 32 px，主要危险按钮不小于 34 px；
- 长路径、格式徽标、删除数量、错误原因和主按钮不被截断；
- 高度不足时只滚动上方内容，底部动作保持可见；
- Filmstrip、照片画布和详情栏遵守已确认的响应式边界。

## 7. 候选构建与安装验证

阶段 8 实施和源码级测试全部通过后才构建 Windows 候选安装包。顺序固定为：

1. 构建一次候选安装包；
2. 记录安装包 SHA-256；
3. 验证全新安装、从上一版本升级和卸载后用户数据保留规则；
4. 从安装目录定位实际 EXE；
5. 记录已安装 EXE SHA-256 并冻结候选；
6. 只针对该已安装 EXE 运行候选级验证；
7. 测试结束后重新计算全部绑定 checksum；
8. 任何不一致使全部候选测试失效。

候选测试启动时必须验证进程映像路径和文件哈希。`src-tauri/target/release` 中的未安装二进制不能代替已安装候选。允许测试入口驱动已安装 EXE，但不得重编译、替换或旁路其生产安全层。

## 8. 冻结候选的安全重测

同一冻结二进制必须在 G 盘专属可丢弃 Root 上重新执行：

- 完整 Import 状态、重复证明、空间门、partial、发布、恢复和全量故障注入；
- 进程级源卷写请求为零，源树内容、名称、可观察元数据和既有照片逐字节不变；
- no-overwrite、完整后缀族、名称抢占和哈希碰撞后逐字节拒绝；
- 完整 Recycle、强制 flags、逐文件回调、SQLite 提交故障、部分结果和 NeedsAttention；
- 永久删除 API、警告确认和任何降级路径均不存在；
- Windows 回收站恢复后文件内容哈希与原文件一致，重扫后没有旧删除标记；
- 缓存所有权、替代对象竞态、未知文件保留和专属目录外零触碰；
- SQLite、备份、迁移、损坏只读模式和 AppData 空间不足；
- 规模、性能、DPI、键盘、对比度和窗口缩放。

测试只能使用生成或明确可丢弃数据，不能导入、回收或删除用户唯一照片。真实图库 Import 和 Recycle 始终保持独立关闭，直到用户在报告交付后另行确认。

## 9. 证据绑定与准入

候选清单至少绑定：

- 候选安装包文件名、大小和 SHA-256；
- 已安装 EXE 的绝对路径、大小和 SHA-256；
- `package-lock.json` 和 `Cargo.lock` SHA-256；
- schema 版本、完整 schema checksum；
- 每份迁移的版本、文本 checksum 和组合 checksum；
- 测试工具版本、报告版本、Run ID、时间和硬件/卷信息；
- 每个机器可读报告的 SHA-256。

Import 和 Recycle 分别生成独立安全报告及独立准入。两份准入绑定同一候选清单，但保持独立开关。共享安全层异常通过全局写入门同时关闭两者。任何候选、锁文件、schema、迁移或绑定报告变化都会使验证器拒绝旧准入；重新构建必须完整重跑。

## 10. 27 条产品验收与缺陷门

上位产品规格第 20 节的 27 条验收条件逐条建立机器可读条目。每条包含条件编号、证据文件、证据 checksum、结果和必要的人工验收记录。没有直接证据、证据范围不足或只依赖旧阶段报告时均记为未通过。

缺陷登记至少包含严重度、数据安全影响、复现、受影响候选哈希和处置。任一未解决 Critical 或高风险数据安全缺陷、任一验收失败、缺证或候选绑定不一致都会阻止 Import/Recycle 准入和 v1 完成标记。

## 11. 交付物与发布边界

最终本地提交包含：

- 阶段 8 机器可读总报告和简短人工报告；
- 独立 Import 安全报告与准入；
- 独立 Recycle 安全报告与准入；
- 27 条验收矩阵；
- 性能、规模、缓存、数据库和可访问性证据；
- 候选清单及全部 checksum；
- 发布说明和已知限制；
- 真实照片启用前的单独确认清单。

发布说明必须明确 Windows 回收站不是照片备份，SQLite 备份也不是照片备份，并披露 `IFileOperation` 最终校验与 Shell 执行之间的非原子残余窗口。

本阶段不推送、上传或发布远端。只有 27 条全部通过、未解决 Critical/高风险缺陷为零、候选绑定完整且两套专项安全报告全部通过后，才允许标记阶段 8 完成并创建最终本地 Git 提交。

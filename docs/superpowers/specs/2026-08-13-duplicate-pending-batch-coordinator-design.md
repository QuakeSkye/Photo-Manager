# 重复文件批量加入待删除协调设计

## 背景

重复复核页允许用户跨整个检测结果勾选多个待删副本，并提供全页面“勾选全部非建议保留”操作。当前前端把全部选择作为一个请求提交，但后端同步接口只能为同一个逻辑照片创建一个 `DuplicateSubset` `DeletionMark`，因此跨照片选择会被拒绝。错误又显示在确认弹框背后的页面上，用户看到的表现是点击“加入待删除”后没有反应。

现有安全约束本身合理：一个 `DeletionMark` 只属于一个逻辑照片，待删除快照、撤销、批次和回收流程都以逻辑照片为边界。本设计不放宽该约束，而是在它上方增加后端批量协调层。

## 目标

- 一次接受重复复核页当前确认的全部选择。
- 按逻辑照片建立多个独立的 `DuplicateSubset` 标记。
- 整批严格原子：任一选择失败时，一个标记也不创建。
- 长时间复证在后台执行，确认弹框持续显示进度并允许取消。
- 发现第一个失败项后立即停止，不继续读取后续文件。
- 全部成功后刷新待删除快照并进入图库右侧待删除页面，继续使用既有复核和 Windows 回收站流程。

## 不变的安全边界

- 一个活动 `DeletionMark` 仍然只绑定一个 `PhotoId + photoVersion`。
- 同一照片中选择的 JPG/RAF 可以属于同一个 `DuplicateSubset` 标记。
- 每个待删 Asset 必须绑定一个未选择的同角色保留 Asset。
- 加入待删除前仍需完成内容相同和文件身份稳定证明。
- 真正回收前仍按现有流程再次验证待删端、保留端和 Root/Binding 身份。
- 最终文件动作只能进入 Windows 回收站；批量协调不移动、修改或直接删除照片。

## 方案选择

采用后端批量协调任务。前端一次提交全部选择，后端负责分组、预检、复证、进度、取消和原子提交。

不采用以下方案：

- 同步长请求：无法可靠提供进度和取消，仍会表现为无响应。
- 前端拆分多个单照片请求：中途失败会产生部分标记，无法满足整批原子性。
- 删除后端的同照片检查：会破坏待删除模型、快照和回收流程的所有权边界。

## 批量任务模型

应用进程中同一时间只允许一个重复文件加入待删除任务。任务保存在内存，不新增数据库批次表。

任务阶段：

| 阶段 | 含义 | 是否可取消 |
| --- | --- | --- |
| `validating` | 解析选择、按照片分组并逐项复证 | 是 |
| `committing` | 在一个 SQLite 事务中建立全部标记 | 否 |
| `completed` | 全批提交成功 | 已结束 |
| `failed` | 首个预检、复证或提交错误 | 已结束 |
| `cancelled` | 用户取消验证 | 已结束 |

任务状态至少返回：

- 任务 ID 与提交 `operationId`。
- 当前阶段。
- 总待删物理文件数、已验证文件数。
- 总容量与已验证容量。
- 当前待删文件路径和对应保留文件路径。
- 成功时的逻辑照片数、物理文件数和总容量。
- 失败时的待删路径、保留路径、稳定错误类别、用户提示和内部诊断。

## 数据流

```text
用户确认整批选择
        ↓
start_duplicate_pending_batch
        ↓
创建唯一内存任务并立即返回
        ↓
按 PhotoId + photoVersion 分组
        ↓
整批结构与版本预检
        ↓
逐个待删/保留文件流式复证
        ↓
全部成功
        ↓
阶段切换为 committing
        ↓
一个 SQLite 事务为每个逻辑照片创建独立标记
        ↓
返回 completed
        ↓
刷新图库和待删除快照
        ↓
切换到 #/pending-delete
```

## 预检与分组

后端不信任前端分组，必须从数据库重新解析全部 Asset 与 Photo 关系，并按 `PhotoId + photoVersion` 分组。开始文件读取前完成以下整批预检：

- 请求非空，`runId`、`operationId` 和所有内部 ID/version 合法。
- 检测 Run 已完成且仍绑定当前图库修订和 RootBinding。
- 每个选择确实属于该 Run 的等价集合。
- 待删端与保留端角色一致，版本仍是当前版本。
- 每个等价集合至少保留一个未选择且当前可靠的成员。
- 同一个 Asset 不被重复选择，保留端不在本批待删集合中。
- 每个逻辑照片当前没有其他活动待删除标记。

发现第一项问题立即把任务置为 `failed`，不执行后续文件读取，不创建任何标记。

## 流式内容复证

当前单项复证会对每对文件执行多轮完整读取。批量任务改用一次同步流式证明：

1. 在受约束 Root 内解析并只读打开待删端与保留端。
2. 读取前验证 file ID、大小、mtime、非 reparse 和当前绑定。
3. 两端按固定块同步读取；逐块比较字节，同时分别计算完整 SHA-256。
4. 每个读取块检查取消标志，目标检查粒度约为 1 MiB。
5. 读取结束后验证长度、SHA-256 和逐字节结果都一致。
6. 在原句柄上再次验证身份，并重新打开路径确认仍是同一身份。
7. 只把成功证明保存在内存任务中，验证阶段不写数据库。

这样减少磁盘读取，但不降低现有“完整哈希 + 逐字节比较 + 前后身份复核”的证明强度。

## 原子提交与幂等

全部选择复证成功后，任务进入 `committing`。后端在一个 SQLite `IMMEDIATE` 事务内：

1. 再次验证 Run 修订、所有 Asset/Photo 版本和活动标记冲突。
2. 为每个逻辑照片生成独立 `DeletionMarkId`。
3. 为每个标记写入待删 Asset 快照、保留端快照和 retention guard。
4. 为每张照片写入一个确定性子操作事件，并让对应标记引用该子操作。
5. 任一写入、约束或提交故障都使整个事务回滚。

现有 `operation_event` 只能关联一个结果实体，因此不把一个事件复用于多个标记，也不新增批次表。后端按稳定的照片排序，从“批次 `operationId` + `PhotoId` + 领域分隔符”确定性派生每张照片的子 `OperationId`。每个子操作记录该照片规范化选择的请求哈希，并以对应 `DeletionMarkId` 作为结果实体；`DeletionMark.created_operation_id` 继续准确指向自己的子操作。

批次 `operationId`、规范化后的整批请求哈希和确定性子操作共同定义幂等性：

- 首次提交在同一事务中写入全部子操作和标记。
- 相同批次 ID 与相同规范化请求重试时，必须证明所有预期子操作及标记都已存在且一致，然后返回同一批结果。
- 只存在部分预期子操作视为数据库链不一致并进入安全错误，不能补写剩余标记。
- 相同批次 ID 搭配不同请求时，派生身份或请求哈希冲突，必须拒绝。

提交完成前数据库中的新活动标记数始终为零；提交完成后一次出现全部标记。

## 取消、退出与恢复

- `validating` 阶段允许取消。取消标志在调度等待和每个读取块之间检查。
- 点击取消后弹框显示“正在取消”；当前阻塞读取返回后停止。
- 取消会丢弃全部内存证明，不创建标记，并把弹框恢复到原确认摘要。
- 原选择保持不变，用户可以重新确认或关闭弹框调整选择。
- `committing` 阶段不接受取消，因为只剩短暂原子事务；按钮禁用并显示“正在加入待删除”。
- 验证期间应用关闭或崩溃，内存任务消失，数据库没有任何标记。
- 提交期间应用崩溃，由 SQLite 保证全提交或全回滚。
- 如果提交已成功但前端尚未跳转，重启后现有待删除摘要仍会发现全部标记。

不需要为验证任务增加启动恢复记录，也不增加数据库迁移。

## 后端接口

### `start_duplicate_pending_batch`

输入 `runId`、整批 `operationId` 与全部选择。若已有 `validating` 或 `committing` 任务则拒绝第二个任务。成功时立即返回初始状态，不等待文件复证完成。

### `get_duplicate_pending_batch_status`

返回当前或最近一次任务状态。前端在弹框打开期间每 250–500ms 轮询；任务终态后停止轮询。

### `cancel_duplicate_pending_batch`

只在 `validating` 阶段设置取消标志并返回最新状态。`committing` 或终态调用返回稳定状态，不制造第二种结果。

旧同步入口不再由前端调用。单照片标记创建逻辑降为事务内部函数，继续复用其数据库安全校验。

## 确认弹框交互

初始摘要继续显示全部待删路径、保留路径、格式、文件数和容量。用户点击确认后，弹框保留并切换状态：

### 验证中

- 标题显示“正在验证待删除文件”。
- 显示 `正在验证 X / N`、已验证容量和总容量。
- 显示当前待删路径及保留路径。
- 主确认按钮禁用，取消按钮改为“取消验证”。
- 不允许通过 Escape 或关闭弹框隐藏仍在运行的任务。

### 正在提交

- 显示“正在加入待删除”。
- 所有操作按钮禁用，等待短暂事务完成。

### 失败

- 立即停止进度并恢复可操作弹框。
- 在弹框内部显示首个失败待删路径、保留路径、原因和下一步。
- 保留全部原选择，允许用户关闭后修复，或在条件恢复后重新确认整批。
- 错误不得只显示在弹框背后的主页面。

### 取消

- 不显示为失败。
- 恢复原确认摘要和按钮。
- 选择保持不变。

### 成功

- 清空重复复核页已提交选择。
- 关闭弹框。
- 刷新图库快照与待删除快照。
- 选中待删除页第一项并切换到 `#/pending-delete`。

## Fail-fast 错误分类

| 类别 | 用户提示与下一步 |
| --- | --- |
| 文件身份或版本变化 | 文件已变化，请重新检测后再选择 |
| 待删端或保留端离线/缺失 | 恢复文件或图库连接后重试 |
| 两端不再完全一致 | 内容已不同，请重新检测 |
| 已有活动待删除标记 | 先到待删除页处理该照片的现有标记 |
| 检测结果过期 | 重新检测重复文件 |
| 数据库忙或提交失败 | 稍后重试；本批没有创建标记 |
| 用户取消 | 恢复摘要，不作为错误 |

内部诊断保留技术细节；用户提示不建议绕过证明、直接修改数据库或永久删除文件。

## 验证标准

### 后端

- 跨多个逻辑照片的一次批量提交成功，为每张照片创建一个独立标记。
- 同一照片的 JPG/RAF 选择归入同一个标记。
- 任一结构预检或文件复证失败时，活动 `DuplicateSubset` 标记数保持为零。
- 首个失败后后续文件不再被打开或读取。
- 取消后无标记，任务进入 `cancelled`。
- 最终事务中间故障时全部回滚。
- 同一批次幂等重试不重复创建标记；冲突请求被拒绝。
- 同时启动第二个任务被拒绝。
- 验证进程退出后无孤立数据库任务或标记。
- 提交完成事实可在前端未跳转或重启后通过待删除快照恢复。

### 前端

- 初始弹框仍准确列出全部待删与保留路径。
- 验证阶段显示文件数、容量、当前两端路径和取消状态。
- `validating → committing` 后取消入口禁用。
- 失败原因显示在弹框内，并保留全部选择。
- 取消后恢复摘要并保留选择。
- 成功后刷新快照并进入 `#/pending-delete`。
- 轮询错误有可见提示，不让弹框永久停留在假进度状态。

### 回归

- 单照片与同一照片 JPG/RAF 的重复清理继续成立。
- 普通图库 D/R 标记与撤销不变。
- 待删除页复核、回收确认、Windows 回收站执行和结果协调继续通过。
- 文件身份变化、保留端丢失和数据库故障仍以不删除待删文件为安全结果。

## 非目标

- 不允许部分成功；任一失败都使整批零提交。
- 不在前端拆分请求或实现补偿性撤销。
- 不改变一个逻辑照片一个活动标记的模型。
- 不把验证任务持久化为可恢复后台作业。
- 不增加跳过失败项、自动重试、永久删除或绕过回收站选项。
- 不修改重复扫描算法；精确文件名预筛由独立设计处理。

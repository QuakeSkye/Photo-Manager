# 导入响应性与 JPG/RAF 配对修复设计

## 背景

当前内存卡导入存在三个连续问题：

1. 只读预检通过同步 Tauri command 在主线程执行递归枚举、媒体解析和完整 SHA-256，Windows 窗口消息、进度查询与取消请求无法及时调度，窗口显示“未响应”。
2. 用户在最终确认框点击“开始导入”后，前端等待同步 `start_import` 返回；该调用会在返回前完成全量计划验证、空间检查、复制、验证、发布和索引。界面一直显示“正在确认”，即使内存卡已经读取且目标机械盘已经写入。
3. 预检能够把同名 JPG/RAF 归入同一个 ImportGroup，但导入索引只写入基础文件身份，丢失已经解析的媒体元数据，也没有使用 `SameImportGroup` 证据协调 Photo。每个物理文件分别创建 Photo，界面出现互补的 `JPG ✓ / RAF ×` 与 `JPG × / RAF ✓`。

## 目标

- 预检、验证和正式导入期间保持窗口、状态查询和取消操作响应。
- 最终确认只负责接受导入任务；接受后立即进入真实的验证或导入状态，不把实际复制伪装成“正在确认”。
- 保留现有全量计划验证、完整哈希、空间门、partial、no-replace 发布、持久化恢复和来源零写入约束。
- 新导入的同组 JPG/RAF 立即形成一个 Photo，并保留完整可用的媒体元数据。
- 应用启动后的后台增量扫描安全修复已经受本缺陷影响的导入组，不修改照片文件。

## 非目标

- 不移除或缩短确认后的全量只读计划验证。
- 不引入通用任务队列或重写现有 ImportJob/Attempt 状态机。
- 不自动配对没有可信导入证据且历史元数据不足的任意同名文件。
- 不原地更新不可变的 `asset_media_metadata`、`pair_evidence` 或其他历史事实。
- 不使用用户唯一照片执行自动测试。

## 方案选择

采用定向后台化方案，复用现有后台图库扫描和持久化导入状态：

- 预检通过 Tauri 阻塞线程池运行。
- 正式导入由独立后台工作线程运行，命令只启动任务并立即返回状态。
- 配对使用已有 ImportGroup、PublishedFact、IndexedFact 和 `SameImportGroup` 证据。
- 已有错误数据在启动增量扫描的协调阶段修复。

仅把 command 标记为 `async` 不能修正“命令直到整次导入完成才返回”的接口语义，也会让同步文件 I/O 占用异步运行时工作线程。引入通用 JobRunner 则超出本次缺陷范围。

## 一、只读预检后台化

`start_import_preflight` 在进入后台前完成轻量准入检查，并克隆所需的 `Arc` 服务。递归枚举、EXIF/RAF 解析、完整哈希和草稿规划通过 `tauri::async_runtime::spawn_blocking` 执行。

预检服务继续拥有唯一状态：

- 启动前原子切换到 `Running`，拒绝第二个预检。
- 每个文件更新扫描数量、支持文件数量和当前相对路径。
- 成功后写入 `Completed` 和草稿。
- 取消后写入 `Cancelled`，不保留可确认草稿。
- 失败后写入 `Failed` 与用户可读错误。

`get_import_preflight_status` 和 `cancel_import_preflight` 保持短命令。后台任务不能持有状态 Mutex 进行文件 I/O，状态锁只用于快照或单次更新。

## 二、确认与后台导入

### 启动边界

`start_import` 的语义改为“接受并启动任务”，而不是“执行整次导入并返回结果”。服务增加进程内唯一工作线程门：

1. 验证写入安全门和草稿摘要。
2. 原子取得唯一工作线程所有权，拒绝重复点击或并发重试。
3. 在短数据库事务中创建初始 TaskIntent、ImportJob 和 Confirmed Generation，或确认已有任务的 Proposed Generation；只有该事务提交后，任务才算被接受。
4. 在启动线程前把公开状态设为 `ValidatingPlan`。
5. 启动命名后台线程执行现有导入流程。
6. 立即返回当前 `ImportExecutionStatus`。

后台线程仍按原顺序执行：全量刷新计划、验证 generation、检查空间、创建 Attempt、复制、验证 partial、no-replace 发布、索引、关闭 Attempt 和报告。现有数据库事实与安全边界不改变。

工作线程无论成功、领域错误或 panic 都必须释放进程内工作门。领域错误转换为可查询状态；panic 被记录为内部错误并关闭 Import/Recycle 共享写入安全门，避免静默留下可继续写入的假健康状态。

### 前端状态

前端点击确认后等待的只是启动结果：

- 返回 `validatingPlan` 或 `running` 时立即关闭模态框，显示执行面板并开始轮询。
- `validatingPlan` 显示“正在全量验证导入计划”，不得显示“正在确认”。
- `running` 显示当前文件、当前动作、完成/发布/跳过/失败/未开始数量。
- `awaitingPlanConfirmation`、`awaitingSpace`、`awaitingSource`、`needsAttention` 使用现有交互继续处理。
- 启动命令自身失败时保留确认框并显示错误，因为任务尚未被接受。

关闭应用导致后台线程中断时，不自动重放写操作。下次启动继续由现有 `reconcile_startup` 根据已提交事实进入等待、需要关注或可重试状态。

## 三、导入配对与元数据

### 新导入

预检不再只保留 `capture_local_key`。内部 `SourceFile`/`ExecutionDraftSeed` 携带本次媒体解析得到的规范化字段：

- 拍摄本地时间键；
- 相机型号和序列号；
- 拍摄参数；
- JPG 源预览或 RAF 内嵌 JPEG 的预览状态和偏移。

这些字段只存在于进程内确认草稿种子，不扩大前端可编辑计划。发布后的目标文件已经通过源哈希与 partial 哈希验证，索引时可把同一份解析证据写入目标 Asset 的首个不可变元数据版本，无需再次解析整份照片。

一个 ImportGroup 的 JPG 和 RAF 都完成索引后，目录层使用 `import_group.pair_evidence='SameImportGroup'` 作为正向证据，创建 `pair_evidence.evidence_kind='SameImportGroup'` 的 PairEvidence，并把两个 Asset 合并到一个活动 Photo。配对动作必须确认：

- ImportGroup 恰好有一个 JPG Step 和一个 RAF Step；
- 两个 Step 都有 PublishedFact 和 IndexedFact；
- 两个目标 Asset 当前仍为 Present；
- 当前 AssetRevision 文件身份与各自发布快照一致；
- 两个 Asset 尚未被其他冲突的活动配对占用。

任一条件不满足时不自动配对，并把任务或扫描报告标记为需要关注。

### 已有错误数据修复

应用启动且已绑定图库时，现有 `start_background_if_bound` 启动全量或增量扫描。扫描完成目录观察后，在同一后台流程执行一次 Import 配对协调：

1. 查询 `import_group.pair_evidence='SameImportGroup'` 的已确认 ImportGroup。
2. 通过 PublishedFact、IndexedFact 和目标 Asset 找到对应 JPG/RAF。
3. 将当前 AssetRevision 与发布时 FileIdentitySnapshot 比较。
4. 身份一致时补建不可变 SameImportGroup PairEvidence 并合并 Photo。
5. 身份变化、缺项、重复角色或证据链不完整时保持拆分并记录扫描问题。

已有空 `asset_media_metadata` 行是不可变历史，不原地更新，也不伪造文件变化来创建新 AssetVersion。配对修复依赖更强的导入事实，因此不要求改写旧元数据。未来导入从首个版本起写入完整元数据。现有补充拍摄参数表继续按解析器版本执行自身的只读扫描补齐逻辑。

## 并发与错误处理

- 图库扫描、预检和正式导入继续遵守现有互斥与 I/O 调度策略。
- 预检工作线程启动失败时，在返回前恢复运行门并产生可操作错误。导入工作线程启动失败时，已提交的任务进入可恢复的需要关注状态，不回滚或伪装为未接受。
- 正在运行的导入拒绝第二次启动；取消只请求停止未开始项，不撤销已发布事实。
- 配对协调在数据库短事务中执行，不在事务内读取或哈希文件；文件身份数据来自扫描观察和既有发布快照。
- 配对事务失败不得影响已发布照片文件或把导入错误标记为成功。
- 所有修复保持来源内存卡零写入，目标正式文件也不因配对修复发生写入。

## 测试与验收

### 预检

- 受控慢速预检运行期间，状态查询能返回且计数持续增长。
- 取消请求能在后台任务完成前生效。
- 重复预检被拒绝，完成或失败后运行门释放。
- Windows 冒烟验证窗口不出现“未响应”，当前路径和计数可见。

### 后台导入

- 受控执行器阻塞复制时，`start_import` 已返回 `ValidatingPlan` 或 `Running`。
- 前端确认框在任务接受后关闭，验证与复制显示真实阶段。
- 覆盖重复启动、取消、空间不足、来源离线、计划变化、工作线程错误和启动恢复。
- 现有完整哈希、partial、发布、no-replace、故障注入、来源零写入与报告测试继续通过。

### 配对

- 导入一组同名 JPG/RAF 后，时间线只有一个 Photo，显示 `JPG ✓ / RAF ✓`。
- 新导入 Asset 首版保存拍摄时间和可用媒体元数据。
- 旧缺陷夹具在启动增量扫描后通过 SameImportGroup 自动合并。
- 当前文件身份变化、缺少角色、角色重复或事实链不完整时不自动合并。
- 修复前后照片文件大小、mtime 和 SHA-256 不变。

### 完整验证

运行 Rust 单元与集成测试、前端测试、格式检查、静态检查和生产构建。自动测试仅使用生成夹具或明确可丢弃的照片副本，不读取或写入用户唯一照片。

## 实施顺序

1. 后台化预检并验证状态查询、取消与窗口响应。
2. 拆分确认和后台导入，验证状态、并发门及恢复。
3. 贯通新导入元数据、使用 SameImportGroup 配对，并加入启动扫描修复。
4. 运行完整回归和生产构建。
